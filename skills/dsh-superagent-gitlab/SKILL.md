---
name: dsh-superagent-gitlab
description: Read GitLab issues, merge requests, discussions, pipelines and repository files using glab.
---

Workers use orchestrator_read for repository context when needed: gitlab/issues/<iid> or gitlab/merge_requests/<iid> for the description and facts; append /notes/<page> or /discussions/<page> for its conversation; gitlab/merge_requests/<iid>/pipelines for its head pipelines; gitlab/pipelines/<id>/jobs for a pipeline's jobs; gitlab/merge_requests/<iid>/approvals for its approval state when the instance serves it. gitlab/repository reads the checked project: gitlab/repository for the default branch, gitlab/repository/files/<path> for a file, gitlab/repository/tree/<path> for a directory, and gitlab/repository/branches or gitlab/repository/branches/<name> for branches. A page holds 100 entries and names next_resource while another may follow. A message is `{ id, from, at, text, reply_to?, path?, line?, discussion?, resolvable?, resolved?, url? }`: `id` is GitLab's note id, `reply_to` the first note of its discussion, `path` and `line` an inline diff note's file and line, `discussion` the discussion to reply in or resolve, `resolvable`/`resolved` whether that thread can be and is resolved, and `bot: true` marks a bot or service account, whose words never authorize work. Follow next_offset to finish the current response; offset 0 reads afresh, later offsets the same snapshot. System notes (assignment, review requests, approvals, merges) are not messages. Reading does not create tickets or send replies. Allowed mentions subscribe the issue/merge request; subscribed notes arrive without further mentions; merge requests authored by the deployment's GitLab account are subscribed automatically and changed CI on a subscribed merge request is delivered.

Use glab for every GitLab call, never gh, and never another account or credential: the worker environment points glab at the agent account through `GITLAB_HOST`. Always name the instance and the project: set `HOST="${DSH_SUPERAGENT_GITLAB_URL#*://}"` and `PROJECT=$(printf '%s' "$DSH_SUPERAGENT_GITLAB_PROJECT" | sed 's|/|%2F|g')`, then call `glab api "projects/$PROJECT/..." --hostname "$HOST"`; GitLab does not accept the unencoded project path, and glab without `--hostname` silently targets gitlab.com. Query parameters go in the path string; send JSON bodies (arrays, `position`) with `--method POST -H "Content-Type: application/json" --input <file>`, because fields alone cannot express them. `DSH_SUPERAGENT_GITLAB_MR_HEAD` is the current merge request's head ref when the ticket started on one.

Reply with `glab api "projects/$PROJECT/merge_requests/<iid>/discussions/<discussion>/notes" --hostname "$HOST" --method POST -f "body=<text>"` for a note of a merge request discussion, or the same path with `discussions` replaced by `notes` for a plain issue or merge request note; for an inline diff note reply use the discussion the read named, which keeps the reply in place. A new inline note needs a `position` built from the merge request's `diff_refs` that gitlab/merge_requests/<iid> returned: `{"body":"...","position":{"position_type":"text","base_sha":<base_sha>,"start_sha":<start_sha>,"head_sha":<head_sha>,"old_path":"<path>","new_path":"<path>","new_line":<line>}}` posted to the merge request's `discussions`. Resolve a thread the ticket settled with `glab api "projects/$PROJECT/merge_requests/<iid>/discussions/<discussion>?resolved=true" --hostname "$HOST" --method PUT`, and unresolved with `resolved=false`; only threads the read marks `resolvable` can be resolved. Replies the host queues for review threads already carry a hidden `<!-- dsh-superagent:<id> -->` marker; never post a host reply by hand or resolve a thread the host is about to answer. The approvals API depends on the GitLab tier and may answer 403 or 404: treat that as "no approval data", never as a failure, and read approval and merge system notes as facts rather than as messages.

Read a merge request's head pipeline before judging CI: gitlab/merge_requests/<iid>/pipelines lists it and gitlab/pipelines/<id>/jobs each job; a pipeline that is `created`, `pending`, `waiting_for_resource`, `preparing`, `scheduled` or `manual` has not failed and must never be reported as one, and an Auto DevOps project with no runners keeps pipelines pending forever. Changes of a subscribed merge request's head pipeline arrive as CI triggers; answer the ones that ask the ticket for work, and read the pipeline for every job before reporting a failure or a recovery.

`main` and other protected branches accept a push only from a role the project's protected-branch rule allows: check `DSH_SUPERAGENT_GITLAB_PUSH_ALLOWED` before pushing a branch directly, and open a merge request otherwise. Never merge a merge request, and never enable merge-when-pipeline-succeeds, unless the Delivery requirements section explicitly asks for it and `DSH_SUPERAGENT_GITLAB_MERGE_ALLOWED` is true; merge as the project's merge method and checks require, naming the head sha, never force-push a protected branch, and record the merge request number with `orchestrator_report mr_number` immediately after creating or adopting it.

Before substantial work on a new human request or review comment, call `orchestrator_ack` with its original trigger ID and a brief request-specific `text`, even within an existing ticket; the host replies once in that source thread. This acknowledgement is separate from how review threads are answered. Do not acknowledge bots or CI. Record the bot run identifier, review-round count and dispositions in `orchestrator_report`; the merge request description retains the final implementation, verification and material limitations.
